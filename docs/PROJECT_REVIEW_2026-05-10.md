# 项目评审（用户视角）

日期：2026-05-10

## 总体结论

项目已经具备一个可用的 Windows 端流媒体/本地播放器雏形，功能覆盖面较好。
但从“普通用户实际安装和长期使用”角度，当前最大风险不在功能缺失，而在**跨平台可用性、版本一致性、稳定性可观测性**。

## 主要问题（按影响程度）

### 1. 发布信息存在版本不一致，容易造成用户困惑

- `README` 标记当前版本为 `v1.1.0 (2026-05-08)`。
- `CMakeLists.txt` 里 `project(... VERSION 1.1.0)`。
- `src/main.cpp` 中 `app.setApplicationVersion("1.0.0")` 仍是 1.0.0。

影响：用户在“关于页面/日志/反馈问题”时难以对应实际版本，排障效率会明显下降。

建议：统一单一版本源（例如 CMake project version），在编译期注入到应用内显示。

### 2. 跨平台承诺与实际可用状态差距较大

- README 写明 Linux/macOS 为 Planned 且未测试，Android 仍在集成中。
- CMake 对 Android 采用 stub 模式（禁用 GStreamer 依赖）。

影响：用户看到“支持平台”后可能预期可运行，但实际体验会落差明显，影响项目可信度。

建议：在 README 顶部增加“当前稳定平台仅 Windows x64”的醒目提示，并给出其它平台里程碑。

### 3. 运行依赖复杂，首次安装门槛偏高

- Windows 依赖 Qt + GStreamer + VS 工具链，且需要手动配置环境。
- `main.cpp` 通过运行时路径猜测 GStreamer 插件目录，说明部署路径稍有变化就可能失效。

影响：用户遇到“能启动但无法播放”这类问题概率较高，且不容易自助定位。

建议：
- 提供“完整便携包”和“安装器”两种分发；
- 在启动时增加依赖自检（插件目录、关键解码器是否可用）并给出可读错误提示。

### 4. Known Issues 仍偏抽象，缺少用户可执行指引

- 当前仅列出 Android 未完成、Linux/macOS 未测、硬解兼容性不一。

影响：用户遇到问题后不清楚临时规避方案。

建议：把问题拆成“症状-原因-临时解法-计划修复版本”格式。

## 其他优化建议

1. 增加“快速开始（5分钟）”章节：下载、运行、测试流地址、常见报错处理。
2. 增加崩溃/黑屏日志收集说明，降低用户反馈门槛。
3. 对关键特性做兼容性矩阵（协议/编码/封装/硬件）。
4. 在每次发布附“已知回归风险”与“回滚方法”。

## 优先级建议（两周内）

- P0：修复版本号不一致（1.1.0/1.0.0）。
- P0：README 增加稳定平台声明和支持边界。
- P1：增加启动依赖自检与明确报错文案。
- P1：补充 Known Issues 的临时解决方案。
- P2：完善 Linux 最小可运行验证（哪怕仅 CI smoke test）。
